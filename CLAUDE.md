# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**RVC Learn** (`rvc/learn`) — a learning-management system for วิทยาลัยเทคนิคร้อยเอ็ด (Roi Et Technical College). PHP 8.1+, Slim 4 + PHP-DI, Latte templates, MariaDB 10.4+. All user-facing strings and code comments are in Thai; keep it that way.

The full teacher/student/admin experience is implemented (branch `feature/lms-teacher-flow`): role-aware dashboards, courses + units (หน่วยการเรียน — see the schema section; the old `lessons` table is gone), an AI quiz generator and lesson-plan generator (streamed over SSE), a review-before-publish queue, BYOK AI settings, student quiz-taking with auto-grading, and an admin AI/quota dashboard. `project/RVC Learn.dc.html` is the visual spec these were built from.

**Quiz generation, lesson-plan generation and the test chat all call the real API** (`AiRouter::route(..., real: true)`); `SimulatedProvider` is now only the fallback path when `real` is false. The central AI machine is called **AI ของส่วนกลาง** in the UI (never "AI ของวิทยาลัย"), though the routing source key stays `college` in code and the DB.

`README.md` is **not** about this codebase — it is a design handoff bundle note from Claude Design pointing at `project/RVC Learn.dc.html` (an HTML/CSS design prototype under `project/`).

Run `/admin/demo` (admin only) to load realistic ปวช./ปวส. demo data. Demo accounts: teacher `thanaphon`, students `66201001`–`66201028`, password `rvclearn2569`.

## Commands

```bash
composer install                    # install dependencies (required before anything works)
composer serve                      # dev server at http://localhost:8080 (php -S, docroot public/)
```

Then open `http://localhost:8080/install.php` to run the 4-step installer (requirements → database → site/admin → install). The installer creates the database, runs migrations, seeds settings + admin user, and writes `config/config.php` + `storage/install.lock`. Step 3 has an opt-in "ใส่ข้อมูลตัวอย่างด้วย" checkbox (off by default) that runs `DemoSeeder` via `install_demo()`; because the seeder truncates courses and deletes teacher/student accounts, it is skipped (with a log line) whenever the database already has courses or non-admin users, and a seeding failure never fails the install. Re-running `install.php` after install requires authenticating as an admin user.

There is **no test suite, linter, or build step** configured. `composer.json` has no `require-dev`. If adding tests, PHPUnit is the natural choice but nothing is wired up yet.

Database migrations are run through the web UI at `/admin/migrations` (admin only) — run / rollback last batch / reset all / preview SQL. There is no CLI migration runner.

**Deploy**: pushing to `main` deploys to production — `.github/workflows/main.yml` SSHes in, `git reset --hard origin/main`, then `composer install --no-dev` (it fails loudly if composer is missing). Migrations are **not** run by the pipeline; an admin runs them at `/admin/migrations` afterwards. A newly added composer package is therefore only safe once `composer.lock` is committed; `phpoffice/phpspreadsheet` (student import/template) additionally degrades to CSV / a Thai message if the library is absent.

## Architecture

### Request lifecycle
`public/index.php` → checks `vendor/` and `Config::isInstalled()` (redirects to `install.php` if not) → starts session (`RVCSESSID`) → `app/bootstrap.php` builds the PHP-DI container, creates the Slim app, sets base path from `app.url`, registers a custom error handler that renders `error.latte` with Thai messages per status code → loads `app/routes.php` → `$app->run()`.

### Trailing slashes
Routes are declared without a trailing slash (`/courses`, not `/courses/`), and Slim treats the two as different paths — so a hand-typed `/courses/` used to render the Thai 404 page. A middleware registered in `bootstrap.php` *after* `addRoutingMiddleware()` (Slim runs middleware LIFO, so it executes before routing) strips the trailing slash and redirects: 301 for GET/HEAD, 308 for anything else so the method and body survive. The app root (`/` or `/cvm.kmr/`) is left alone.

### Key seams
- **`App\Support\Config`** — immutable dot-notation accessor over `config/config.php` (a `return [...]` PHP array). `Config::write()` is installer-only. `config/config.php` is gitignored and must never be committed.
- **`App\Support\Paths`** — all filesystem paths, derived from its own location so `install.php` can use it before `vendor/` exists. `install.php` manually `require`s `Paths.php` + `Requirements.php` when there is no autoloader.
- **`App\Support\Database`** — PDO factory (`connect` with db, `connectServer` without) + server version inspection. Enforces `utf8mb4`, `STRICT_TRANS_TABLES`, real prepares.
- **`App\Support\View`** — thin Latte wrapper; `render()` injects shared vars + `flash` (`Flash::pull()`) + `csrf` (`Csrf::token()`) into every template.
- **`App\Support\Url`** — static base-path holder; use `Url::to('/path')` for internal links, `{$base}/path` in templates.
- **`Csrf`** / **`Flash`** — session-backed. Every state-changing POST checks `Csrf::check($data['_token'])`; forms include `<input name="_token" value="{$csrf}">`.

### Auth
`App\Auth\Auth` owns everything: `attempt()` (with throttling — 5 failed attempts / 15 min per username-or-IP via `login_attempts` table), session start with `session_regenerate_id`, `user()` lookup, `log()` to `audit_logs`. Two PSR-15 middlewares: `AuthMiddleware` (requires login, sets `user` request attribute, redirects to `/login`) and `RoleMiddleware([...])` (throws `HttpForbiddenException`). Routes in `app/routes.php`: public login group, then an auth group (`ViewContext` + `AuthMiddleware`) with per-role subgroups.

**Roles** live in `App\Auth\Roles` — never compare role strings inline, use its constants and sets. Besides `admin` / `teacher` / `student` there is **`supervisor` (ผู้ดูแลครู)**: a teacher an admin promoted to also oversee everyone. `Roles::TEACHING` (teacher + supervisor) guards every teacher route, so a supervisor keeps their own courses; `Roles::OVERSIGHT` (admin + supervisor) guards `/admin/users` (list + approve/reject registrations) and `/admin/courses` (all courses, plus `/admin/courses/{id}` and `/admin/courses/{id}/units/{unitId}` — read-only inspection of any teacher's unit content, every review status). Everything else under `/admin` stays admin-only: AI + quota, migrations, logs, system settings, demo data, impersonation, password resets, and role assignment itself. Admins appoint roles at `POST /admin/users/{id}/role` (`UsersController::changeRole()`, refuses changing your own role, demoting the last active admin, or touching student accounts). `Roles::label()` gives the Thai name; `ViewContext` shares it as `$roleLabel`, and `layout.latte` derives `$teaches` / `$oversees` from the role for the sidebar. Migration `000115` added the enum value.

**Impersonation**: an admin can assume another (non-admin, active) user via `POST /admin/users/{id}/impersonate` — `Auth::impersonate()` stashes the admin's id in `$_SESSION['impersonator_id']` and swaps `user_id`/`user_role` (without touching the target's `last_login_at`). While impersonating, admin routes 403 as expected; a sticky banner (shared as `impersonatedBy` by `ViewContext`) and the header button post to `POST /impersonate/stop` (`Auth::stopImpersonating()`, outside the role subgroups). `AuthController::logout` also detects impersonation and restores the admin instead of ending the session. `Auth::log()` adds `via_admin_id` to meta during impersonation.

### Migration system (`app/Migration/`, `database/migrations/`)
Custom, Laravel-flavored. Files named `YYYY_MM_DD_NNNNNN_snake_case.php` containing one class extending `App\Migration\Migration` (class name = StudlyCase of the part after the timestamp, e.g. `CreateCoreTables`). Each migration implements `description()` (Thai), `up(Runner)`, `down(Runner)` and calls `$this->table('name')` (applies the configurable table prefix) and `$this->options()` (shared `ENGINE=InnoDB ... utf8mb4`).

- **`Migrator`** — discovers files, tracks state in the `<prefix>migrations` table, runs pending in filename order (`sort(SORT_STRING)`, so the **date prefix wins over the `NNNNNN` number** — e.g. `2026_09_12_000108` runs before `2026_09_14_000106`; date a new migration after the latest file) stopping on first failure, batches, rollback/reset, MySQL `GET_LOCK` around runs.
- **`Runner`** interface with two impls: **`LiveRunner`** executes SQL; **`DryRunner`** just records it. `preview()` and `declaredTables()` use `DryRunner` to get SQL without touching the DB — `declaredTables()` regex-parses `CREATE TABLE` names so the installer's "fresh install" drops only *this system's* tables, never co-tenant tables sharing the database.

Prefix awareness is pervasive: `Auth`, `Migrator`, `Installer`, controllers all take the prefix from `db.prefix` config and interpolate it into backtick-quoted table names. When writing queries, follow this pattern — there is no query builder or ORM.

### Schema domains (migration files)
`000101_create_core_tables` (users, remember_tokens, login_attempts, settings, audit_logs), `000102_create_lms_tables`, `000103_create_assessment_tables`, `000104_create_ai_tables`; later ones are incremental (`ls database/migrations`).

`000108_restructure_units` is the big one: a course is a list of **units** (`units`), each bundling an intro (`key_content` / `objectives` / `competencies`), a pre-test (`quizzes.kind='pretest'`, ungraded), content sections (`unit_sections`, `type` = text / video / pdf), worksheets (`assignments.unit_id`) and a post-test (`quizzes.kind='posttest'`, graded). Student progress lives in `unit_progress` + `section_progress`; `courses.pass_threshold` is the course pass mark. It migrated and dropped `lessons` / `lesson_attachments` — `quizzes.lesson_id` / `assignments.lesson_id` are legacy columns. Other notable additions: `000109` discussion boards (`BoardController`, `/board`), `000111` per-course admin switches `ai_quiz_enabled` / `ai_lesson_plan_enabled` (`POST /admin/ai/courses/{id}/features`), `000112` institutions, `000113` password-reset links (`/reset-password/{token}`), `000114` course-code uniqueness per teacher.

### Data access & AI layer
- **`App\Support\Db`** — thin PDO helper. `{table}` in SQL expands to the prefixed backtick-quoted name; `first/all/value/int/run/insert/update/transaction`. All repositories in `app/Domain/` take a `Db`. There is no ORM.
- **`app/Domain/*Repository`** — one per aggregate (Course, Unit, Assignment, Quiz, Enrollment, Attempt, Review, Board, Institution, StudentAccount, Settings, Ai, LessonPlan; `LessonRepository` predates the unit restructure). `SettingsRepository` also caches the `settings` table and stores per-user prefs as `name:userId` keys.
- **`App\Support\ViewContext`** middleware (on the auth group) shares `user`, `term`, and teacher `reviewCount` into every Latte render.
- **`app/AI/`** — `AiProvider` interface (`stream()` yields plain text chunks as they arrive), the real providers plus `SimulatedProvider`, `QuestionBank` (real vocational questions by subject, used by the simulator), `Prompt` (spec → Thai instruction) and `JsonStream` (text → JSON objects), `QuizGenerator` / `LessonPlanGenerator` (stream → structs), `AiRouter` → `AiRoute` (provider + source label + chip + wait + quota flag), `KeyCipher` (AES-256-GCM over `app.key`), `AiUnavailableException` (`reason` drives `_partials/ai-state.latte`).
- Lesson plans are stored as `ai_generations` rows (`target_type='lesson_plan'`, doc JSON in `payload`), not a dedicated table.

### Short AI drafts (no SSE)
Quizzes and lesson plans stream over SSE because they run long. Everything else that asks the model for a short structured draft goes through **`App\AI\Drafter::objects($userId, $system, $spec, $limit)`** instead: it routes (`real: true`), streams to completion inside the request, feeds the text through `JsonStream::objects()`, drops the trailing `{"done":true}` line, writes `ai_usage_logs`, and returns plain arrays. Callers add a `task` to `Prompt::userText()` and a Thai `$system` line — **never pass an empty system prompt**, Google rejects it and the request dies before the model sees anything.

Three features use it, all following the same "AI proposes → teacher confirms → save as draft" shape: `UnitOutlineController` (`/courses/{id}/units/design`, task `unit_outline`, designs the whole unit list from the course description), `UnitController::draftContent()` (task `unit_content`, writes the text sections of one unit; proposals sit in `$_SESSION['unit_content_draft']` and render as checkboxes on the unit editor), and `AssignmentController::draft()` (task `assignment`, drafts a worksheet's objective/steps/deliverable/rubric into the form fields). Failures are caught, logged through `LoggerInterface` so `/admin/logs` has the real reason, and shown to the teacher as a Thai flash. `Drafter::objects()` releases the PHP session lock (`session_write_close()`) while waiting for the model and re-opens it afterwards — otherwise every other page the teacher has open hangs until the draft finishes; the "สั่งเพิ่มเติม" note on all three forms is a multi-line `textarea.note-input` (≤ 2000 chars). `HttpClient` streams abort after 180 s with no bytes at all (`CURLOPT_LOW_SPEED_*`) instead of waiting the full 600 s. Models are sloppy, so `Drafter` also unwraps a wrapper object (`{"units":[…]}` → its items) and `Drafter::text()` flattens list values (objectives/competencies sent as arrays used to render as "Array") into one-item-per-line text; `UnitOutlineController` asks once more for the missing units (passing the drafted titles as `existing`) when the model stops short of the requested count. The `unit_outline` prompt says "**new** units, N more, not counting the existing ones" explicitly — the old "design N units" + "don't repeat these" wording made a reasoning model (Pathumma qwen3-think) loop on total-vs-additional until it timed out with no JSON at all. Clearer wording alone did not stop it (still 2 of 3 runs failed), so `Drafter` sets `no_think` on the spec when the routed model name matches `/qwen3|think/i` and `Prompt::userText()` appends Qwen3's `/no_think` switch — 3 of 3 runs then finished in ~25 s.

### SSE generation flow
Quiz/plan generation streams over `text/event-stream` (`QuizWizardController::stream`, `LessonPlanController::stream`): `ignore_user_abort(true)` + `set_time_limit(0)` so the job finishes and persists even if the browser closes; events are `meta` / `question`|`section` / `done` / `error`. The result is always saved server-side as a draft + a pending `ai_generations` row regardless of the client. Both controllers pass the teacher's `userQualityPref()` through to the provider, and both bail out with reason `empty` (rendered by `_partials/ai-state.latte`) rather than saving an empty draft when the model returns nothing parsable.

### Real AI providers vs. the simulator
`app/AI/HttpClient.php` (cURL + `curl_multi`, so `lines()` is a generator that yields as bytes arrive) backs three real providers: `GoogleAiProvider` (Gemini `streamGenerateContent?alt=sse`), `OpenAiCompatibleProvider` (`/chat/completions` with `stream:true` — OpenRouter or any base_url; it deliberately sends no `max_tokens`, because self-hosted servers reserve KV cache for it and answer ~20x slower), `OllamaProvider` (`/api/chat` NDJSON, `isAvailable()` probes `/api/tags` with a 2s timeout). `AiRouter::route(..., real: true)` builds those instead of `SimulatedProvider`, and every generation path passes it. `Prompt::userText()` turns the JSON spec into the actual instruction the model sees — the chat spec becomes its plain message, while `quiz` and `lesson_plan` become Thai prompts that spell out the exact NDJSON shape `QuizGenerator` / `LessonPlanGenerator` parse. Because small local models rarely obey "one JSON per line", both generators read the stream through `JsonStream::objects()`, which brace-counts its way through code fences, prose and pretty-printed JSON and yields each complete object as soon as it closes. It only tracks `"` **inside** an object (prose with an odd number of quotes before the JSON used to make it treat the rest of the stream as one string and return nothing) and skips reasoning models' `<think>…</think>` blocks, even when a tag is split across chunks — if the stream ends with the think block still open (a reasoning model that rambled and answered inside it), it re-reads everything after `<think>` without skipping. HTTP failures become `AiUnavailableException` with a Thai message (`HttpClient::describeError`), reason `key_invalid` on 401/403. `SettingsController::probeKey()` is a real check: list models, then a one-token generate call (a key can list models yet be denied generation).

### Multiple providers, multiple models, per-task choice
Both sides hold **many providers, each with many enabled models**: central providers are `ai_endpoints` rows (admin-managed, `is_active`, one `is_default`), teacher keys are `user_api_keys` rows (a teacher may connect several; `saveKey()` no longer disables older keys, `disableKey()` removes one). Each row keeps `model` (= the main model, first in the list) plus `models_enabled` (JSON list); `AiRepository::enabledModels($row)` reads it (falls back to `model`, `['']` = let the provider pick) and `modelFields($posted)` cleans a posted `models[]` list for saving. Central rows also have `models_unlimited` (JSON subset, migration `000120`): models the admin marked "ใช้ได้ไม่จำกัด" (e.g. free models) — `AiRouter` skips the quota check for them and returns `countsQuota: false`, so `consumeQuota()` is never called.

An **AI option** is one provider × one model, identified as `c{endpointId}:{model}` or `k{keyId}:{model}` (split on the first `:` only — Ollama model names contain colons). `AiRouter::options($userId)` lists everything the user may pick (their own active keys, then active central providers; each with `group`, `label`, `online`, `free`). `route($userId, …, target: $id)` tries, in order: the target passed with the task → the teacher's default (`ai_target:{userId}`, set at `POST /settings/ai/default`) → each source's main model in `ai_route:{userId}` order (the default's source wins) → central unlimited models as a last resort (so a teacher who has used up the quota still gets a free model). `resolve()` re-checks ownership (`keyForUser()`), `is_active` and that the model is enabled, so a forged id just falls through. `AiRoute->target` is what actually ran; the chat stream's `meta` event carries `switched: true` when it differs from the request.

Per-task pickers: the floating chat has a `<select id="aichatAi">` fed by `GET /ai/chat/status` (`options` + `default`; the choice is kept in the chat's `sessionStorage` state as `ai` and sent as `&ai=` on the stream URL); the quiz wizard and lesson-plan form include `_partials/ai-picker.latte` (`name="ai"`, hidden when there is only one option) — the quiz `ai` rides the query string through `workspace` into `stream` and is stored in the generation `params` so "regenerate one question" reuses it. `Drafter` forms (unit outline, unit content, worksheet draft) include the same picker: `Drafter::picker($userId)` returns `options` + the last choice (`$_SESSION['ai_pick']`), and `Drafter::objects(…, $target)` routes to it. Model lists in both settings pages use `public/assets/js/model-picker.js` (`RvcModelPicker(box, {name, selected, unlimitedName?, unlimited?})`: search, tick many, "ตั้งเป็นหลัก" reorders, custom names, and on the admin page a per-model "∞ ไม่จำกัด" toggle posted as `unlimited[]`). Teachers fetch a saved key's model list with `POST /settings/ai/keys/{id}/probe` (uses the stored key) and save with `POST /settings/ai/keys/{id}/models`; the connect wizard shows the picker after a successful test.

### Chat attachments
The chat input takes up to 8,000 characters (`AiChatController::MAX_MESSAGE`). Because `EventSource` can only issue GET requests and a Thai character costs 9 bytes once URL-encoded, the message is **not** put in the query string — that blew past Apache's 8,190-byte `LimitRequestLine` and failed with 414 at roughly 900 Thai characters. Instead `POST /ai/chat/prepare` stashes the message (plus attachment ids) in the session and returns an id, and `GET /ai/chat/stream?p=<id>` consumes it once (`pullPrompt()` deletes it after reading) and accepts one file at a time (up to 3 per question, 2 MB each) via `POST /ai/chat/attach` or drag-and-drop onto the panel. `App\Support\TextExtract` pulls plain text out of txt/md/csv/json/xml/html directly, out of .docx through `ZipArchive` + `word/document.xml`, and out of PDFs best-effort by inflating streams and reading text operators — a scanned PDF raises a Thai message telling the teacher to attach .docx/.txt instead. Extracted text (capped at 20,000 chars) lives in `$_SESSION['ai_chat_files']` keyed by a random id, newest 3 kept; the stream request passes `attach=<id,id>` and `attachedText()` prepends the file contents to the message before the session lock is released. This is what lets a teacher attach a course outline and say "สร้างรายวิชาตามไฟล์นี้".

### AI actions from the chat
The floating chat can act, not just talk: when a **teacher** asks it to create a course, the system prompt (`AiChatController::systemPrompt()`) tells the model to answer with a single `{"action":"create_course",…}` object. `stream()` sniffs the first non-blank characters — a leading `{` (after any ``` fence) switches it to action mode, so the JSON is never shown as chat text; `parseAction()` then emits an `action` SSE event and the panel renders a confirmation card. Nothing is written until the teacher presses the button, which POSTs to `/ai/chat/create-course` (teacher-only route, CSRF-checked, re-validates the code against `codeTaken()` and files the course in the current term) and logs `ai.chat.create_course`.

The second action is `create_unit`: the model drafts a unit (`title`, `key_content`, `objectives`, `competencies`) plus 3–6 text `sections`, and `parseAction()` attaches the teacher's own course list to the payload so the confirmation card can show a course `<select>` (preselected when the model's `course_code` matches). Confirming POSTs to `/ai/chat/create-unit`, which re-checks ownership with `ownedByTeacher()`, writes the unit as `source='ai'`, `review_status='draft'` and its sections as `type='text'`, then logs `ai.chat.create_unit` — the teacher edits and publishes it from the normal unit editor. `cleanSections()` caps it at 12 sections / 20k chars each.

Adding another action means extending the system prompt, `parseAction()`, the card renderer (`actionCard()` dispatches by `d.action`), and a teacher-only write route.

Small models often break the "answer with JSON only" rule (prose before the JSON, a code fence, or no `"action"` key at all), so `stream()` also keeps the full text of a text-mode reply and, for teachers, re-runs `parseAction()` on it when the reply ends — a JSON object found there turns into an `action` event and the client swaps the text bubble for the card. `parseAction()` infers the action when it is missing (`code`+`name` → `create_course`, `title`+`sections` → `create_unit`). Course **ท-ป-น** (theory hours/week – practice hours/week – credits) is never trusted to the model: `AiChatController::tpn()` regex-reads it from the teacher's message + attached files (a `\d-\d-\d` triple on the same line as ท-ป-น / หน่วยกิต / ทฤษฎี, ignoring course codes and dates; when the line says the third number is self-study hours it uses ท + ป/2) and overrides the model's numbers (`tpn_from_source`). The `create_course` card shows ท / ป / น as editable number inputs with a hint when credits ≠ ท + ป/2.

### Floating AI chat
`_partials/ai-chat.latte` (included from `layout.latte` for teacher/admin only) is a floating assistant panel available on every page: `GET /ai/chat/status` returns the current `AiRoute` chip as JSON, `GET /ai/chat/stream` streams a plain-text reply as `meta` / `delta` / `done` / `error` SSE events. `AiChatController` calls `AiRouter::route(..., enforceQuota: false, real: true)` so it hits the teacher's actual API at their own quality preference — chatting never burns college quota, but it still writes `ai_usage_logs` + an `ai.chat.test` audit row. The stream calls `session_write_close()` after the CSRF check so it does not hold the session lock while streaming.

The transcript survives page navigation: the panel script keeps `{open, draft, files, items}` in `sessionStorage` under `rvc.aichat.{userId}` (per tab, per user — deliberately not `localStorage`, classroom PCs are shared) and `restore()` redraws it on every page. Every element in the log is tied to an item via `track(el, item)`; remove elements with `drop(el)`, never `el.remove()`, or the item comes back on the next page. Item types are `me` / `ai` (with `partial` while streaming — a reply cut off by navigation gets a Thai "ถูกตัด" note) / `note` (optional `link`) / `card` (a pending action card, re-rendered with `actionCard(d, item)`). The model still gets no chat history — each message is answered on its own.

### Teacher-managed courses
Teachers create and edit their own courses: `GET /courses/new` and `GET /courses/{id}/edit` render `courses/edit.latte`, `POST /courses[/{id}]` runs `CourseController::save()` (shared by create and edit), `POST /courses/{id}/archive` sets `status=archived` — courses are never deleted because lessons, quizzes and attempts hang off them. `CourseRepository::codeTaken($teacherId, …)` guards the `uk_course_teacher_term` unique key (teacher + code + term + classroom — two teachers may each own a course with the same code) with a Thai message instead of a SQL error; on any validation failure `save()` redirects back to the form it came from.

### RMS import (บุคลากร / กลุ่มเรียน / นักเรียน)
`/admin/rms` (admin only, `Admin\RmsController`) pulls from the college RMS. **`App\Integration\RmsClient` is the only code that talks to RMS**: host from setting `rms_base_url` (validated `^https?://`), path `/api_connection.php` + `app_name=nutty` hard-coded (no SSRF via settings), 60s timeout; failures throw `RmsException` with a Thai message. `App\Integration\RmsSync` does the upserts, all idempotent: `people` → `users` (match `people_id` or non-student `username`; new = role teacher, password from `ath_pass` only on create; never touches role/password afterwards; people gone from RMS are `suspended` with `rms_deactivated_at`, and only those get re-activated automatically — an empty RMS reply deactivates nobody). `std2018_studentgroup` → `classrooms` keyed by `group_code`, newest term wins, advisor matched by full name. `std2018_student` → student `users` (username = studentCode, initial password = idcard, `rms_student_id`, `classroom_id`) + `student_profiles`; loaded 100 at a time by the page's JS loop (count first, stop when `fetched < row` or `done >= total`; `row` clamped server-side). The idcard is never stored. Migration `000117_add_rms_sync`. Emails that collide with another account's (unique column) are dropped rather than failing the row. Not implemented: `dateedu`, `stopday`, `studing`.

### Printable lesson plan (สอศ. 2567)
`GET /courses/{id}/plan-print` (`PlanPrintController`, owner-only, opened from the "พิมพ์แผนการสอน" button on the course page) renders `plan/print.latte`, a standalone A4 document in the OVEC 2567 competency-based plan format: cover, ลักษณะรายวิชา + approval signatures, unit/hours table, then one plan per unit (สาระสำคัญ, สมรรถนะ, จุดประสงค์, เนื้อหา, กิจกรรม, สื่อ, หลักฐาน, การวัดผล, บันทึกหลังสอน) built from the unit's intro fields, sections, worksheets and pre/post-tests. Hours are (theory+practice) × 18 weeks split evenly across units. `courses.objectives` / `courses.competencies` (migration `000118`, one item per line, editable on the course form and filled by the AI chat `create_course` card) feed ลักษณะรายวิชา. Every sheet is `contenteditable` so teachers fill fields the schema lacks (CLOs) before printing — edits are not saved. Font is TH Sarabun New via `local()` or `public/assets/fonts/THSarabunNew*.ttf`, falling back to Google Sarabun at a smaller size with an on-screen warning.

### Joining a course (enrollment)
Students enroll themselves — nothing else writes `enrollments` except `DemoSeeder`. Each course has a 6-char `courses.join_code` (migration `000116`, alphabet without O/0/I/1, generated lazily by `CourseRepository::joinCode()` the first time the teacher opens the **นักเรียน** tab) and a `join_enabled` switch. That tab shows the code + the absolute link `/join/{code}` with copy buttons; `POST /courses/{id}/join` with `do=open|close|regenerate` (`CourseController::joinSettings()`). Students either type the code (or paste the whole link — `normalizeJoinCode()` extracts it) into `_partials/join-form.latte` on their dashboard and `/learn`, posting to `POST /learn/join`, or open `GET /join/{code}` (auth group, no role guard so staff get a friendly message), which renders a confirm page — opening a link never enrolls by itself. `JoinController::problem()` rejects unknown/archived/closed courses and a teacher from a different `institution_id`; `EnrollmentRepository::enroll()` reactivates `dropped` rows but leaves `completed` alone. `AuthMiddleware` remembers the GET URL in `$_SESSION['intended']` and `AuthController::login` returns there (same-site paths only), preselecting the student tab when it is a join link.

Teachers can also enroll students directly on the same tab by email: `POST /courses/{id}/students` (`CourseController::addStudents()`) splits the textarea on whitespace/comma/semicolon, and `StudentAccountRepository::activeByEmail()` looks up **existing** active student accounts (case-insensitive, limited to the teacher's `institution_id` when set). Student emails are optional and not unique, so an email matching several accounts is skipped rather than guessed; no account is ever created from an email. The result comes back as separate flashes (added / already enrolled / not found / ambiguous / invalid).

### Student quiz list
Students only ever see quizzes through `QuizRepository::publishedForStudent()`: `review_status='published'` **and** at least one question (so a teacher's draft/pending quiz is invisible by design), with the student's own open attempt, finished count and best graded score. `StudentController::decorateQuizzes()` adds the Thai button/state text and `_partials/quiz-row.latte` renders the row (pass `q:` explicitly on `{include}` — loop variables are not inherited). `/learn/{courseId}` nests each quiz under its published unit and collects quizzes with no unit, or whose unit is still unpublished, under a trailing "แบบทดสอบ" list so a published quiz never disappears; `/learn/units/{id}` shows pretests above the content and posttests below. Every button POSTs to `/learn/quizzes/{id}/start`, which resumes an in-progress attempt instead of starting a new one.

### Admin-managed central AI
`/admin/ai` is split into server-rendered tabs via `?tab=overview|settings|quota|courses` (`AiController::TABS`, invalid values fall back to `overview`, `<a n:class="tab, ...">` links, no client JS). `saveEndpoint()`/`testEndpoint()` redirect back to `?tab=settings` and `saveCap()` to `?tab=quota` (via `redirect($response, $tab)` — `$tab` may carry `&edit=…`).

The **settings** tab lists every central provider (status dot, kind, URL, enabled-model chips with "หลัก" / "∞ ไม่จำกัด", buttons) and opens the edit form with `?tab=settings&edit={id}` or `&edit=new` (`editingEndpoint()`; the form opens by itself when there are no providers yet). `POST /admin/ai/endpoint` saves (hidden `id` = edit, empty = add; the first provider ever added becomes `is_default`), with `models[]` and `unlimited[]` from the model picker, a `kind` = `ollama` | `openai_compatible` | `openrouter` | `google`, base_url (fixed for the hosted kinds), optional API key encrypted with `KeyCipher` (blank keeps the stored one, `clear_key=1` removes it) and notes; it immediately probes the main model and writes `status` + `last_checked_at`, returning to the form when the probe fails. `POST /admin/ai/endpoint/test` probes without saving (posting `id` so the stored key of *that* provider is used) and returns the discovered model list as JSON for the picker; it only rewrites the stored `status` when base_url and main model match what is saved. `POST /admin/ai/endpoint/{id}/active` (`active=0|1`) hides/shows a provider for teachers without deleting it, `/{id}/default` makes it the main provider, `/{id}/delete` removes it (if it was the default, the next one is promoted). Probing means `/api/tags` for Ollama, `GoogleAiProvider::probe()` for Google and `OpenAiCompatibleProvider::probe()` otherwise. Migrations `000106` (kind), `000119` (`models_enabled`, `is_active`, teacher `models_enabled`) and `000120` (`models_unlimited`).

Fonts: Plus Jakarta Sans (headings 800, `letter-spacing: -.025em`) with Noto Sans Thai for Thai glyphs, Outfit (`--accent`) for big numbers, Roboto Mono. Icons are **Material Symbols Outlined** via `<span class="msi">name</span>`; `layout.latte` loads the font with an `icon_names=` subset — **add any new icon name there, alphabetically sorted**, or it renders as plain text.

Layout (`layout.latte`): a 280px full-height sticky sidebar (`.side-brand`, `.side-nav` links whose active item is a solid brand pill — secondary links live in collapsible `.nav-group[data-group]` blocks (teacher: `mine`; oversight: `oversee`; admin: `data`, `system`) that start collapsed unless they hold the current page (`is-here`), remember their state in `localStorage` key `rvc-nav-groups` (applied by an inline `n:syntax="off"` script right after the list, before paint), and are force-expanded while searching or in the icon rail — and a `.side-profile` card at the bottom holding the theme button `#themeButton` and the logout / stop-impersonation form), and a `.main` column with an 80px glass `.topbar`: hamburger `#navToggle`, breadcrumb (`{include title}` re-prints the page's title block), a menu search `#navSearch` (filters `.side-nav` links by `.nav-label`, Enter jumps to the first match — there is no site search), and 42px `.tool-btn` shortcuts (bell → review queue / users / learn by role, gear → AI / system settings / appearance, theme icon `#themeIcon`). The hamburger collapses the sidebar to an 88px icon rail on desktop (`html.nav-mini`, `localStorage` key `rvc-nav`) and opens it as a drawer over `.nav-scrim` on ≤860px (`html.nav-open`). Dashboards open with a `.hero` (radial indigo→violet, 40px radius, blurred circles, `.hero-badge`, `.hero-pill` counters); the teacher dashboard adds a 4-up `.metric-grid` (totals computed in the template from `$courses` / `$quota`) and a 2:1 `.dash-row` of recent work + a dark `.insight-card`. ### Course covers
Every course has its own cover colour, used identically on cards (teacher dashboard, `/courses`, student dashboard, `/learn`, landing) and on the course-page `.course-banner`. `App\Support\Cover::decorate($row)` adds `color` (the teacher's `courses.cover_color`, else a palette colour picked by `crc32(id)` — stable per course, never by list position), `accent` (`Cover::accent()`: `Palette::accentFor()` pulled back toward the base when too bright for white text) and `cover_url`; `CourseRepository::forTeacher()/find()/publicLanding()`, `EnrollmentRepository::coursesForStudent()` and `StudentController::course()` return decorated rows. Templates only set `style="--cc:#{$c['color']};--ca:#{$c['accent']}"` and an optional `<img class="cover-img">` (an `<img>`, not `background-image:url()`, to dodge Latte's CSS escaping); CSS paints the gradient from `--cc`/`--ca` and lays a translucent `--cc` overlay over photos. `Cover::PALETTE` is a **list of `[hex, label]` pairs, not a hex-keyed map** — an all-digit hex like `475569` would become an int key. Teachers set the colour (palette / picker / "สุ่มสีใหม่" / "สุ่ม" = back to the id-based colour) or upload a JPG/PNG/WEBP ≤ 3 MB on the course form (`multipart`, `CourseController::saveCover()` checks the real type with `finfo` + `getimagesize`, stores `storage/uploads/covers/{id}-{rand}.{ext}`, deletes the previous file; `remove_cover=1` clears it). `public/assets/js/cover-picker.js` analyses an uploaded photo in the browser (canvas, 4-bit colour buckets weighted toward saturated colours, darkened by lowering HSL lightness until white text reads) and auto-selects the best match, offering up to five suggestions. Photos are served by `GET /course-cover/{id}` (`CourseCoverController`: logged-in users, or guests for `show_on_landing` courses). Migration `000121`.

Glass cards are separate stacking contexts (`backdrop-filter`), so a dropdown overflowing one card would be painted under the next card; `.card:focus-within` / `.card:has(open .combo-list)` raise the active card (`z-index: 20`).

### Theme colour
The indigo (`6366F1`) in `app.css` is only a default. Every theme colour is a **pair**: `Palette::tokens()` also returns `accent` (curated per preset in `Palette::ACCENTS`, otherwise `accentFor()` rotates the hue 30° — greys get a lighter tint of themselves) plus 4 pastel `bg` stops and dark variants; templates emit them as `--violet` and `--bgGradient`, and every gradient, blurred decoration and coloured shadow in `app.css` is written with `var(--brand)` / `var(--violet)` / `color-mix()` so nothing clashes with a non-indigo theme. The appearance page mirrors `accentFor()` in JS for its live preview — keep the two in sync. `--brand`, `--brandInk`, `--brandSoft` and `--brandLine` are re-declared in a `<style>` block from whatever colour applies to the viewer. `App\Support\Palette` derives that whole set (light **and** dark variants) from one hex, and `SettingsRepository::uiPrimary($userId)` resolves it: the user's own `ui_primary:{userId}` first, otherwise the site-wide `ui_primary` that an admin set, otherwise `Palette::DEFAULT`. `/settings/appearance` (any logged-in role) offers twelve presets (Indigo first; Google blue and the old teal `0E6B60` kept as options) plus a colour picker with live preview, Save for yourself, an admin-only "set as everyone's default", and a Reset that clears the personal override. Hex values are stored and emitted **without** `#` — the template writes the `#` itself, per the Latte CSS-escaping gotcha.

Coverage is site-wide except the public landing page, which intentionally has its own independent `--lp-*` palette (see below) and never references `--brand`. Two layers feed `$ui`: `bootstrap.php`'s `View::class` factory shares the **site-wide** default (`uiPrimary()` with no user id) so it reaches every render — including pre-login pages that never go through `ViewContext` (`auth/login.latte`, `auth/register.latte`, `error.latte`, each carrying their own copy of the `<style>` block since they're standalone documents, not `layout.latte` extenders); then `ViewContext` (authenticated group only) overwrites `$ui` with the signed-in user's own colour if they set one. Because `View::renderToString()` always merges the shared array, `$ui` is guaranteed to exist everywhere `layout.latte`'s `{if isset($ui)}` guard now always passes for logged-in pages, and the same guard in the three standalone templates covers guests.

### Latte gotchas
- Interpolating a value that contains `#`, `(`, or `)` **inside** a `style="..."` attribute gets CSS-escaped to `\#` / `\(` (invalid CSS). Put the literal char in the template and interpolate only the safe part: `style="background:#{$c['color']}"` with `$c['color']` = `0E6B60` (no `#`), or use a CSS class (`class="gpu-bar-{$tone}"`). `var(--x)` written literally in the template is fine.
- `class="..."` and `n:class="..."` cannot both be on one element — merge into `n:class="base, cond ? extra"`.
- `n:class` does not do `{}` interpolation; use `class="prefix-{$x}"` or `n:class="'prefix-' . $x"`.
- In inline `<script>`, a `{` followed by a digit is parsed as a Latte tag and **silently removed** — `/^[0-9A-F]{6}$/` shipped to the browser as `/^[0-9A-F]6$/`. Avoid `{n}` quantifiers in templates (check the length separately) or move the script to a `.js` file.
- Anything toggled with `el.hidden` needs the global `[hidden]{display:none!important}` rule in `app.css` to beat class `display` (e.g. `.modal-backdrop{display:grid}`).

## Conventions

- `declare(strict_types=1)` in every PHP file; `final` classes; constructor property promotion; readonly where possible.
- Controllers are `final`, constructor-injected via PHP-DI autowiring, return PSR-7 responses. Note the comment in `routes.php`: Slim route closures must **not** be `static`.
- Templates: Latte in `resources/views/`, `.latte`, extend `layout.latte` via `{block content}`. Thai UI text, `data-theme` dark-mode toggle stored in `localStorage`.
- Assets are plain CSS in `public/assets/css/app.css` — no bundler, no npm.
- Web root is `public/`; `config/` and `storage/` sit outside it, with root `.htaccess` rewriting everything into `public/`.
